6  Runner, events, and separate sessions

The ADK development interface supplies a runtime automatically. A custom Python application needs to construct that runtime itself. The Runner coordinates an agent invocation with a session service and returns an asynchronous stream of events. Understanding that stream explains why a final response is only one part of an agent run.

6.1 One invocation, several events

A question can produce a model response containing a function call, a tool response, and a final natural-language answer. A graph may also emit node-related information and structured outputs. Printing every event as if it were a completed answer produces confusing interfaces. Ignoring every event except the final text discards evidence needed for debugging.

This diagram describes the order example’s tool cycle. Actual event order depends on the invoked agent and available tools.

6.2 Session identity

A session holds a conversation’s events and state. Memory is a separate concept for information retrieved across conversations. An in-memory session service is convenient for learning, but its contents disappear when the Python process ends. The official session overview explains these distinctions.

The supplied runner example is started from the course root:

uv run python -m examples.run_agent "What is the total for 3 bikes at EUR 499.95 each?"

The implementation creates a session, constructs a Runner, passes a google.genai.types.Content user message, and iterates over run_async. Text from a final response can be extracted with a guard:

if event.is_final_response() and event.content:
    text = "".join(part.text or "" for part in event.content.parts or [])

The guard handles content without text. A model response can contain function calls, and a workflow can expose structured output instead of a final text part. A general UI must handle these cases deliberately.

6.3 State is an application contract

A clarified reporting period can live in session state. A product identifier passed from one graph node to another can live in the graph output. These are different data paths. Using session state for every intermediate value can leave stale values after a failed run. Explicit node input and output contracts reduce that ambiguity.

Application identity, user identity, and session identity must be kept consistent. A browser conversation cannot safely reuse a hard-coded shared session for all users. A new session per conversation isolates histories; real deployments also require authenticated users and access controls. Random identifiers alone do not establish authorization.

6.4 Exercise: compare two histories

Two fresh sessions receive different initial questions. A follow-up in the first session refers to its own earlier order; the second session receives a question that would require the first session’s history. A small trace records session IDs, authors, function calls, results, and final-response flags without credentials.

Expected result: the first conversation can use its own history, while the second does not inherit it.

Success criteria: no cross-session order or question leaks into the second answer, intermediate events remain distinguishable from final output, and restarting the in-memory process demonstrates loss of local history.
