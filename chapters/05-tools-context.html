5  Function tools and context engineering

A function tool connects a language decision to a controlled Python operation. Its name, parameter types, and docstring describe when and how it should be used. Its body defines what actually happens. The model proposes arguments; Python validates and executes the operation.

5.1 A small tool contract

The supplied calculate_order_total(unit_price, quantity) function accepts an explicit EUR unit price and integer quantity. It returns currency, total as a decimal string, and quantity. Its arithmetic core is:

price = Decimal(str(unit_price))
total = (price * quantity).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
return {"currency": "EUR", "total": str(total), "quantity": quantity}

Decimal and ROUND_HALF_UP are imported from Python’s decimal module. The complete source is in examples/first_agent/agent.py. Validation before this core rejects negative or non-finite prices and quantities outside zero to ten thousand. Invalid values raise ValueError; they do not return successful totals. The interface and model must handle failure instead of inventing a result.

Registering tools=[calculate_order_total] makes the function available. Its name, types, and docstring describe its purpose. It does not retrieve prices, apply discounts, include taxes, or check inventory. The official function-tool guide describes ADK’s function wrapping.

A type annotation does not establish a valid business value. Validation belongs inside the tool. JSON conversion and argument boundary behavior require tests rather than assumptions.

5.2 Context has a purpose

Context engineering selects the information available at a particular step. For the order example, useful context contains the calculation-tool contract, the current question, and any relevant earlier clarification. A complete unrelated sales export adds volume without resolving the order question.

Four design questions make context decisions concrete:

Decision Global Bike example
What must be supplied? Currency, metric definition, permitted schema
What should be retrieved? The relevant product or bounded query result
What should be retained? A clarified date range within the conversation
What must be isolated? Another user’s question and database results

Tool results are data. A product description containing “ignore previous instructions” does not gain authority merely because it came from a database. The application must preserve the distinction between trusted instructions and untrusted source text.

5.3 Narrow capabilities

A tool named run_anything(code) would give the model broad execution authority. A tool named category_revenue() can return a bounded aggregation without accepting executable code. Narrow functions are easier to document, test, and constrain. The BI project later allows candidate SQL, but inserts a parser-based gate and read-only database permissions before execution. It never executes model-generated Python to create a chart.

5.4 Exercise: improve a tool’s failure behavior

A local variation introduces a maximum order amount. Tests cover an accepted amount, the exact boundary, and a rejected amount. The docstring and instruction describe the policy without inventing business justification.

Expected result: each input produces a documented result that the application can handle without guessing.

Success criteria: the successful result stays factual, failure messages do not invent replacements, and the change does not grant an unrelated capability. A before-and-after trace identifies whether better tool descriptions improved argument selection; one successful conversation alone is insufficient evidence.
