16  Optional extensions and engineering decisions

The core project provides a local agent, deterministic tools, a graph, session handling, an interface, and an evaluated BI pipeline. Extensions should solve a demonstrated problem. Adding a protocol, vector database, or autonomous loop without such a problem increases complexity and the number of boundaries that need testing.

16.1 Retrieval before a query

A larger database may require retrieval of a relevant schema fragment. A schema-retrieval tool can return approved table names, column descriptions, join keys, and metric definitions. Its output remains subject to the SQL execution allowlist. Finding a table in a document does not grant permission to query it.

A useful retrieval experiment compares the full permitted schema with a smaller retrieved fragment on the same question set. Accuracy, missing-column failures, token usage, and latency show whether the additional component helps. A schema summary that omits a currency column can make an answer less reliable despite reducing context size.

16.2 Bounded review and repair

A failed SQL proposal can be returned to a drafting agent with a structured reason. A loop must have a maximum attempt count and a clear terminal failure. The same gate validates every attempt; a reviewer agent cannot waive the gate. A failure after the final attempt is reported to the interface without execution.

This is an optional design, not a claim that the supplied baseline retries. The retry counter and the validator are trusted code. A retry limit controls iteration, while a database timeout controls one execution; both are needed if this extension becomes runnable.

16.3 Persistent sessions and artifacts

In-memory sessions disappear when the process ends. Persistence adds storage, retention rules, and access controls. A deployment must decide which data is saved, who may retrieve it, and how it is deleted. Artifacts such as exported charts or tables also require ownership and provenance. The official ADK artifacts documentation describes the framework component, but application storage policy remains a separate responsibility.

A useful experiment restarts a local persistent-session prototype and verifies both continuity and isolation. It tests two users, missing authorization, and deletion. The mere fact that a conversation survives a restart does not prove that the implementation is safe for shared use.

16.4 MCP, A2A, and deployment

MCP integrates external tool servers; A2A supports communication between agent applications. Each introduces a remote boundary with authentication, available capabilities, errors, and trust decisions. The ADK MCP guide and A2A introduction are starting points for these optional topics. Neither protocol automatically makes a service trustworthy.

Cloud deployment is outside the local baseline. Publishing requires a separate decision about authentication, billing, secrets, database access, and monitoring. A public URL should not be confused with a private development interface. Deployment changes the audience and consequences, even when the Python code is unchanged.

16.5 Exercise: an evidence-based extension proposal

One extension is specified using a concrete failure from the evaluation chapter. The proposal defines the changed data flow, accepted inputs, stopping conditions, tests, and measurable benefit. It includes a diagram that distinguishes existing and proposed behavior in its caption or surrounding prose.

Expected result: a proposal that another developer can implement and evaluate without guessing the objective.

Success criteria: the extension addresses observed evidence, preserves the query gate and session boundaries, and identifies a simpler alternative. A feature list without a testable benefit is not an engineering argument.
